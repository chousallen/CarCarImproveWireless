CarCar Wireless: Handover Note

For the next TAs and developers who will maintain the HM-10 wireless link between students' PCs and the CarCar cars. This note holds only what the guides do not: where things stood on the handover date, the evidence behind the fixes, the open work, the state of the branches, and the facts only the outgoing owner knows.

Written 2026-11-04 Outgoing 周冠宇 (Kuan-Yu Chou) Repo chousallen/CarCarImproveWireless Scope wireless link only

1. Why this exists

The CarCar cars (an Arduino Mega line-following car) used HC-05 Bluetooth Classic modules to talk to the students' PCs. The connection was unstable and hard to predict. Some Windows PCs could not find the module, and some Macs did not give it a serial (COM) port.

This project replaces the HC-05 with an HM-10 BLE module on the car and offers two ways for the PC to reach it: an ESP32 bridge on USB, or the PC's own Bluetooth. Both are described in TA_GUIDE.md, section 1.

Other items from the original improvement proposal (a wiring shield, extra IR sensors, a fixed control rate for the line-following PID loop) are not in this repo and were not started here.

4. Fixes made during the handover

All on 2026-11-04, each tested on the bench. The code is in the git log; this section keeps the evidence, which is nowhere else. Bugs found by reading the code but never seen in use are in section 5, not here.

  1. The scan never restarted after its 30 s window (commit bf417fe, on main). The HM-10 advertised for 60 s after the scan ended and the ESP32 never connected until AT+RESET. The fix starts a new scan when a round ends without a match. Seen on hardware: two empty rounds, then it connected 8 s after the HM-10 was powered.
  2. HM10ESP32Bridge.listen() lost text (commit 2c37117, on main). Each log line was strip()-ed, so a space at the edge of a 20-byte packet vanished ("hello␣" + "world" became "helloworld"), and the part of a packet after a line break had no bt_com: prefix and was thrown away. Confirmed on hardware: a space at byte 20 vanished and abc\r\ndef arrived as abc; the raw ESP32 output was intact, so the fault was in the parser. The fix cuts records at the colour-reset code instead of at line breaks. After it, abc def \r\n, a 20-byte line with a leading space, and 25 bytes with two line breaks all arrived intact.
  3. A reply split across two serial reads was lost (same commit). The parser handled each read on its own, so a line torn between two reads made get_hm10_name() return None and the chat script print "Failed to set name. Exiting." Seen on 2 of 10 tries on Windows and once on Linux. With the fix, the name read correctly 20 of 20 times on Linux and on Windows 11 (the old code: 9 and 14 of 20).
  4. The Windows "Access is denied" error on reopening the ESP32's port (commit 706a882, on main): the old code reproduced it, the new code did not.
  5. Buffer overflow on a long AT+NAME (commit ee37bf8, on main). mes_buff was 11 bytes but the AT+NAME path copied up to 32 bytes into it. The fix enlarges the buffer. The old firmware showed no visible symptom with 25- and 31-character names, so the test shows the fix does no harm but cannot show it repairs anything. Merged because the overflow is real in the code.
  6. OK+CONN came before the link was ready (commit 4b5a6be, not yet on main, section 6). The firmware set connect as soon as the scan found the HM-10, about 0.8 s before notifications were enabled, and data sent in that gap was dropped without any log line. Seen on hardware: 3 of 3 messages lost when sent right after OK+CONN on a reboot, 3 of 3 delivered 1.5 s later. The fix adds a link_ready flag for AT+STATUS? and the send path, logs dropped data, and makes reset() wait for OK+CONN instead of a fixed 6 s. Reconnect takes about 6.3 s on the bench.
  7. ESP-IDF v6.1 (commit 648a97c, not yet on main). The firmware builds on v6.1 with no warnings and still builds on 5.3 and newer. Before this, regenerating sdkconfig gave 2 MB flash in DIO mode instead of the board's 4 MB in QIO mode, because those settings and CONFIG_LOG_COLORS were only in sdkconfig; they are now in sdkconfig.defaults. Flashed and tested with the hardware test, 22 of 22.
  8. Documentation: 5 V wiring for the course's board (commit abe1f3c; the measurement is in TA_GUIDE.md section 4.2), API names and the direct path (804c24b), the split into three guides (6929c99).

5. Open work

The list is DEV_GUIDE.md, section 8, the single home for open issues: add to it there, not here. Reviewed at the handover on 2026-11-04:

  • open, most important Keep testing on different PCs. The direct path depends on each PC's operating system, Bluetooth adapter and driver; the ESP32 path on the CH340 driver. Tested so far: ESP32 path on Linux and Windows 11, direct path on Linux. Untested: macOS on either path, the direct path on Windows. Record each result in section 7.
  • open The AT helpers throw away car data. get_hm10_name(), get_status() and the others discard any BLE data that arrives while they wait for their reply, and listen() drops car messages that start with OK+. From code reading. Until fixed, call the helpers before the chat, not during it; the chat script does.
  • accepted Message format: a newline ends a message, as the student guide shows on both sides. No further work.
  • accepted A failed connect stops the scan (open failed in the log): never seen on hardware, AT+RESET recovers.
  • accepted Unused menuconfig options CONFIG_HM10_DEVICE_NAME / _MAC: harmless.

Two bench observations are recorded in the TA guide's troubleshooting table (section 7) and have no explanation yet: the HM-10's OK+CONN notice twice reached the car corrupted (OK+CON\x00, OK+\x03ONN) while ordinary data never was, and opening or closing the ESP32's serial port once caused an extra disconnect and reconnect.
