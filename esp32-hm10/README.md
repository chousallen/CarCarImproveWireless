# ESP32-HM10 BLE Bridge

ESP-IDF firmware that turns an ESP32 into a bridge between a computer (USB serial) and an HM-10 BLE module. It scans for the HM-10 by name, connects, and forwards bytes both ways. This file is the firmware's usage reference. For the whole system see [TA_GUIDE.md](../TA_GUIDE.md); for building, flashing and the rules that must not be broken see [DEV_GUIDE.md](../DEV_GUIDE.md); for the code, event by event, see [IMPLEMENTATION_NOTES.md](IMPLEMENTATION_NOTES.md).

## Overview

- Scans for a BLE device whose advertised name equals the saved target name, in rounds of 30 s, until it connects
- USB serial (UART0) at 115200 baud, 8N1, no flow control
- Forwards serial data to the HM-10 as BLE writes, and HM-10 notifications to the serial port as `bt_com` log lines
- Four `AT+` commands configure it at run time
- Keeps the target name in NVS (flash), so it survives power cycles and reflashing
- Reconnects on its own after a dropped link

## Requirements

- Any ESP32 board with a USB serial port (the course boards use a CH340 chip)
- An HM-10 that has been set up with `init_hm10/init_hm10.ino` (named, advertising, 9600 baud)
- ESP-IDF v6.1 to build (the committed `sdkconfig` was generated by it from `sdkconfig.defaults`); any version from 5.3 also builds

## Build and flash

See [DEV_GUIDE.md, section 2](../DEV_GUIDE.md#2-build-and-flash-the-firmware). Short form, from this folder:

```bash
idf.py build
idf.py -p /dev/ttyUSB0 flash monitor     # leave monitor with Ctrl+]
```

## Usage

### First run

1. Power the HM-10 so it advertises.
2. Flash the ESP32 and open the monitor. A fresh board looks for the default name `sallen_hm10`; a board that was used before looks for the name saved in NVS.
3. Send `AT+NAME<name>` with the HM-10's name (next section), then `AT+RESET`. The log shows the scan and the connection.

### Bridge commands

Send these over the serial port with **no line ending**, as one write. The ESP32 handles them itself and does not forward them to the HM-10. Use the Python module, or a terminal that sends a whole line at once (Arduino IDE Serial Monitor with "No line ending"); terminals that send each keystroke separately (`idf.py monitor`, `screen`) deliver the characters as separate 10 ms reads, which the firmware treats as data.

**Set the target name.** Saved to NVS; applies after `AT+RESET`.
```
AT+NAMEmy_hm10
```
Reply: `OK+SETmy_hm10`

**Read the target name.**
```
AT+NAME?
```
Reply: `OK+NAMEmy_hm10`

**Read the link state.**
```
AT+STATUS?
```
Reply: `OK+CONN` or `OK+UNCONN`. `OK+CONN` means the link is ready for data: the HM-10 was found, connected, and its notifications are enabled.

**Reboot the ESP32.** It scans again for the saved name.
```
AT+RESET
```
Reply: `OK+RESET`

### Sending data to the HM-10

Once connected, anything else sent to the serial port is written to the HM-10's characteristic `0xFFE1`, in pieces of at most 10 bytes. Text that starts with `AT+NAME` is taken as a command, so do not start a message with `AT`. Data sent before the link is ready (before `AT+STATUS?` answers `OK+CONN`) is dropped, and the log shows `HM-10 link not ready, dropped N bytes`.

### Receiving data from the HM-10

Every notification from the HM-10 (at most 20 bytes each) is printed to the serial port as a log line with the `bt_com` tag:

```
I (12345) bt_com: Hello from HM-10!
```

Command replies use the same tag. The Python module `chat_hm10/hm10_esp32` keeps only these lines; the exact record format and why it must not change are in [DEV_GUIDE.md, section 5](../DEV_GUIDE.md#5-invariants-do-not-break).

## Configuration

### Default settings

```c
// Target device name, used only while no name is saved in NVS
"sallen_hm10"

// UART
UART_PORT_NUM   = UART_NUM_0 (USB serial)
UART_BAUD_RATE  = 115200, 8 data bits, no parity, 1 stop bit, no flow control

// BLE
SERVICE_UUID    = 0xFFE0
CHAR_UUID       = 0xFFE1
```

All BLE and serial parameters (scan interval, MTU, piece sizes) are listed in [DEV_GUIDE.md, section 6](../DEV_GUIDE.md#6-ble-and-serial-parameters).

### Changing the default device name

Edit `target_device_name` in [main/main.c](main/main.c):

```c
static char target_device_name[MAX_DEVICE_NAME_LEN] = "sallen_hm10";
```

This default is used only until a name is saved with `AT+NAME`. After that, the name in NVS wins, even across reflashes. Run `idf.py erase-flash` to clear it.

> **Note:** `main/Kconfig.projbuild` and `sdkconfig.defaults` define `CONFIG_HM10_DEVICE_NAME` (`HMSoft`) and `CONFIG_HM10_DEVICE_MAC`, but `main.c` never reads them. Setting them in `idf.py menuconfig` has no effect.

### Changing UUIDs

If an HM-10 clone uses different UUIDs, change these macros in `main.c`:

```c
#define REMOTE_SERVICE_UUID        0xFFE0
#define REMOTE_NOTIFY_CHAR_UUID    0xFFE1
```

## How it works

### Connection flow

1. **Initialisation**: UART driver and RX task, NVS (loads the target name), BLE stack
2. **Scanning**: rounds of 30 s, restarted until a match is found
3. **Discovery**: an advertisement whose name equals the target name
4. **Connection**: open, then MTU request
5. **Service discovery**: service `0xFFE0`
6. **Characteristic discovery**: characteristic `0xFFE1`
7. **Enable notifications**: write `0x0001` to the CCCD. When this succeeds the firmware sets `link_ready`, and `AT+STATUS?` answers `OK+CONN` from here on (about 0.8 s after the scan found the HM-10)
8. **Data transfer** in both directions; on disconnect, wait 2 s and scan again

### Data flow

**Computer → ESP32 → HM-10:**
```
UART RX → uart_rx_task() → esp_ble_gattc_write_char() → HM-10
```

**HM-10 → ESP32 → Computer:**
```
HM-10 → ESP_GATTC_NOTIFY_EVT → ESP_LOGI(bt_com) → UART TX
```

### Event-driven structure

- **GAP events** (`esp_gap_cb`) handle scanning, connection and disconnection
- **GATT client events** (`gattc_profile_event_handler`) handle service discovery, reads, writes and notifications
- **UART task** (`uart_rx_task`) runs continuously, reads the serial port and handles the bridge commands

## Troubleshooting

Firmware-level symptoms only. The system-level table (ports, drivers, Python errors) is in [TA_GUIDE.md, section 7](../TA_GUIDE.md#7-troubleshooting).

**The log repeats `Scan complete, <name> not found, scanning again`**
- The HM-10 is not powered or not advertising (check with the nRF Connect phone app)
- The saved name differs from the HM-10's name: `AT+NAME?`, then `AT+NAME<correct_name>` and `AT+RESET`
- The HM-10 is already connected to another client

**`HM-10 link not ready, dropped N bytes`**
- Data was sent before `AT+STATUS?` answered `OK+CONN`. Wait for it; the Python bridge's `reset()` does this for you.

**`open failed` in the log and no new scan**
- Known issue: a failed connect leaves the firmware thinking it is connected. `AT+RESET`.

**The link drops often**
- Distance or interference on 2.4 GHz; unstable power to the HM-10

**No `bt_com` lines although the car sends data**
- `AT+STATUS?` says `OK+UNCONN`: not connected
- The log shows `WRITE descr` failed: notifications were not enabled; reset
- The car side is not at 9600 baud

## Logging

Two log tags:

- **`GATTC_HM10`**: system logs (initialisation, scanning, connection, errors)
- **`bt_com`**: data received from the HM-10 and command replies. This tag, at INFO level, is the interface the Python side depends on.

To see only data in the ESP-IDF monitor:

```bash
idf.py monitor --print_filter bt_com:I
```

In a plain serial terminal (PuTTY, minicom, screen), look for lines that start with `I (<timestamp>) bt_com: `.
