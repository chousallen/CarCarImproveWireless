## 2. Build and flash the firmware

Install [ESP-IDF](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32/get-started/) (Espressif's SDK and build system). The committed `sdkconfig` was generated by **v6.1**; any version from 5.3 also builds. Then:

```bash
cd esp32-hm10
idf.py set-target esp32                  # first build in a fresh checkout only
idf.py build
idf.py -p /dev/ttyUSB0 flash monitor     # Windows: -p COM3 ; leave monitor with Ctrl+]
```

- `sdkconfig` is **tracked**, generated by v6.1 from `sdkconfig.defaults`. Put any lasting setting (flash mode QIO, flash size 4 MB, `CONFIG_LOG_COLORS`) in `sdkconfig.defaults`, then regenerate; do not edit `sdkconfig` by hand. `sdkconfig.old` is ignored.
- IDF 6.x no longer pulls `esp_driver_uart` in through the legacy `driver` component, so `main/CMakeLists.txt` names it in `PRIV_REQUIRES`. Warnings are errors; the v6.1 build has zero warnings, keep it that way.
- If `build/` was configured by another checkout, `idf.py` stops with "configured for project ... not ...". Build into another folder: `idf.py -B <dir> build`.
- To flash a finished build without `idf.py` (from `esp32-hm10/`, in ESP-IDF's Python environment; recorded with the v5.5.2 build, check the flash mode against `sdkconfig.defaults`):

  ```bash
  python -m esptool --chip esp32 -p /dev/ttyUSB0 -b 460800 write_flash --flash_mode dio --flash_freq 40m --flash_size 4MB \
    0x1000 build/bootloader/bootloader.bin 0x10000 build/esp32-hm10.bin 0x8000 build/partition_table/partition-table.bin
  ```

- `idf.py erase-flash` clears NVS, including the saved target name. After it, the board uses the `main.c` default (`sallen_hm10`) until a new `AT+NAME` is sent.
- Flashing does **not** clear NVS; the saved name survives.

## 3. Firmware internals

`main.c` is a standard ESP-IDF Bluedroid GATT client plus a UART task. In short:

1. `app_main()` starts the UART driver and `uart_rx_task`, initialises NVS and loads the target name, brings up the BLE stack, requests a local MTU of 500, and registers the GAP and GATT client callbacks.
2. `esp_gap_cb` scans in rounds of 30 s (`esp_ble_gap_start_scanning(30)`). When an advertisement's name equals the target name it stops scanning and opens a connection. When a round ends without a match it logs `Scan complete, <name> not found, scanning again` and starts another round.
3. `gattc_profile_event_handler` walks the usual event chain: connect → MTU → discover service `0xFFE0` → find characteristic `0xFFE1` → register for notifications → write the CCCD. When the CCCD write succeeds it sets `link_ready`; on disconnect it clears `link_ready` and `connect`, waits 2 s and scans again. Two flags: `connect` is set at scan time and only stops a second open; `link_ready` means data can flow (about 0.8 s later).
4. `uart_rx_task` reads at most 10 bytes with a 10 ms timeout, then sleeps 25 ms. If the piece starts with `AT+NAME` it reads up to 32 bytes in total. It handles `AT+RESET`, `AT+NAME?`, `AT+STATUS?` (answers `OK+CONN` only when `link_ready`) and `AT+NAME<name>` itself; everything else is written to `0xFFE1` with `ESP_GATT_WRITE_TYPE_RSP` when `link_ready`, and otherwise dropped with the warning `HM-10 link not ready, dropped N bytes`.
5. Each notification is printed with `ESP_LOGI(TAG_BT_COM, "%.*s", ...)`. The `bt_com` tag is the whole PC-facing data interface (section 5).

Details and the event sequence: [esp32-hm10/IMPLEMENTATION_NOTES.md](esp32-hm10/IMPLEMENTATION_NOTES.md).

## 4. Python modules

**`hm10_esp32_bridge.py`** opens the port at 115200 and keeps a byte buffer. `_read_bt_com_payloads()` finds records with the regex `ESC[..m<L> (<ms>) bt_com: ` and cuts each at the colour-reset code `ESC[0m\r\n`, so a payload may contain spaces and line breaks. An unfinished record stays in the buffer until its end arrives. `\r\n` inside a payload is mapped back to `\n`. The AT helpers (`get_hm10_name`, `set_hm10_name`, `get_status`, `reset`) poll for their specific `OK+...` reply and discard everything else; `listen()` returns all payloads that do not start with `OK+`. `reset(connect_timeout=15.0)` waits 1 s after `OK+RESET`, then polls `get_status()` until it reports `CONNECTED` or the timeout passes; a reconnect takes about 6.3 s on the bench.

**`hm10_bleak_client.py`** uses `BleakScanner.find_device_by_filter` (name and/or address, 10 s timeout), subscribes to `0xFFE1`, and appends each notification to a string buffer that `listen()` returns and clears. `send()` writes 20-byte chunks without response, 20 ms apart, so the HM-10's UART does not overflow.

## 5. Invariants (do not break)

**Interfaces between the parts.** Each link between two parts, what crosses it, and where the details are. There is no other single spec: when you change one side of a link, update the other side and this table.

| Link | What crosses it | Details |
|---|---|---|
| Student code → Python modules | `HM10ESP32Bridge`: `send`, `listen`, `get_hm10_name`, `set_hm10_name`, `get_status`, `reset`, `close`. `HM10BleakClient`: `connect`, `send`, `listen`, `disconnect` (async). | `chat_hm10/hm10_esp32/README.md`, `chat_hm10/hm10_bleak/README.md` |
| PC → ESP32 (USB serial, 115200 8N1) | The four bridge commands, with no line ending. Everything else is data, forwarded in pieces of at most 10 bytes once the link is ready. | [TA_GUIDE.md, section 5](TA_GUIDE.md#5-esp32-bridge-commands), `esp32-hm10/README.md` |
| ESP32 → PC (same port) | One log record per BLE packet or reply: `ESC[0;32mI (<ms>) bt_com: <payload>ESC[0m\r\n`. Inside the payload `\n` is sent as `\r\n`. Every other log line is not data. | Section 4, `hm10_esp32_bridge.py` |
| ESP32 ↔ HM-10 (BLE) | Service `0xFFE0`, characteristic `0xFFE1`. ESP32 → HM-10: writes with response. HM-10 → ESP32: notifications of at most 20 bytes. The ESP32 finds the HM-10 by its advertised name, saved with `AT+NAME`. | Section 6, `esp32-hm10/IMPLEMENTATION_NOTES.md` |
| PC ↔ HM-10 (direct BLE, bleak) | Same characteristic. `send()` cuts text into 20-byte writes without response, 20 ms apart. | Section 4, `chat_hm10/hm10_bleak/README.md` |
| HM-10 ↔ Arduino Mega (Serial3, 9600 8N1) | Raw bytes both ways, no framing. The HM-10 also sends `OK+CONN` / `OK+LOST` when the link goes up or down (`AT+NOTI1`). `AT` sent to the HM-10 while it is connected drops the link. | `init_hm10/init_hm10.ino`, [TA_GUIDE.md, sections 7 and 8](TA_GUIDE.md#7-troubleshooting), `resource/DS-HM10.pdf` |
| PC program ↔ car code (message format) | A newline ends a message; no maximum length. `chat_hm10-bleak.py` and the examples in the student guide end each message with `\n`; the interactive `chat_hm10-esp32.py` does not. | Section 8 |

**Rules:**

- **The `bt_com` log tag at INFO level is the data channel.** The firmware sends HM-10 data and `OK+` replies to the PC as ESP-IDF log lines on UART0, the same port as every other log. `hm10_esp32_bridge.py` keeps only records tagged `bt_com:`. Do not rename the tag, lower the log level, or move the data off the log, unless you change the parser in the same commit.
- **`CONFIG_LOG_COLORS` must stay on** (set in `sdkconfig.defaults`). The parser ends a record at the colour-reset code `ESC[0m\r\n`. Without colours there is no delimiter and every record is lost.
- **`OK+CONN` means the link is ready for data** (notifications enabled, `link_ready`). The bridge's `reset()`, `chat_hm10-esp32.py` and the hardware test send right after `OK+CONN` and expect the data to arrive.
- **`CONFIG_LIBC_STDOUT_LINE_ENDING_CRLF`** makes the ESP32 send each `\n` in a payload as `\r\n`; the parser maps it back. Keep the two in step.
- **The record format** is `ESC[0;32mI (<ms>) bt_com: <payload>ESC[0m\r\n`.
- **Bridge commands** are exactly `AT+NAME<name>`, `AT+NAME?`, `AT+STATUS?`, `AT+RESET`, sent with no line ending. Their replies are `OK+SET<name>`, `OK+NAME<name>`, `OK+CONN`/`OK+UNCONN`, `OK+RESET`.
- **NVS beats the default.** The name saved with `AT+NAME` survives reflashing. The `main.c` default applies only after `idf.py erase-flash`.
- **`CONFIG_HM10_DEVICE_NAME` / `CONFIG_HM10_DEVICE_MAC`** in `Kconfig.projbuild` and `sdkconfig.defaults` are defined but never read by `main.c`.
- **`HM10ESP32Bridge.close()`** must be called before reopening the same port. Windows refuses a second open ("Access is denied").
- **Run the Python scripts from `chat_hm10/`** so the package imports resolve.
- **`.gitignore`** has CRLF line endings on its older lines; match the existing ending when editing it.

## 6. BLE and serial parameters

| Parameter | Value | Where |
|---|---|---|
| Service / characteristic UUID | `0xFFE0` / `0xFFE1` (16-bit, expanded with the Bluetooth base UUID) | `REMOTE_SERVICE_UUID`, `REMOTE_NOTIFY_CHAR_UUID` in `main.c`; `CHAR_UUID` in `hm10_bleak_client.py` |
| Payload per BLE packet | 20 bytes (HM-10 ATT MTU 23) | HM-10 limit; the ESP32's MTU request of 500 is negotiated down |
| Scan | interval 0x50 (80 ms), window 0x30 (48 ms), rounds of 30 s | `ble_scan_params`, `esp_ble_gap_start_scanning(30)` |
| ESP32 → HM-10 write | at most 10 bytes per write, with response, every 25 ms, only while `link_ready` | `uart_rx_task` |
| PC → HM-10 write (direct) | 20 bytes per write, without response, 20 ms apart | `HM10BleakClient.send` |
| USB serial | 115200 8N1, no flow control; driver RX/TX buffers 2048 bytes | `uart_init`, `UART_BUF_SIZE` |
| HM-10 ↔ Mega | Serial3, 9600 8N1, set by `init_hm10.ino` | |
| HM-10 name | 12 characters at most; the bridge's `AT+NAME` reads 32 bytes in total | HM-10 limit; `MAX_DEVICE_NAME_LEN` |

## 7. Hardware test and bench tips

The ESP32 path has an end-to-end test, `tests/hw_e2e.py`: it drives PC → ESP32 → BLE → HM-10 → Mega → PC and back through `HM10ESP32Bridge` and the chat script itself (AT replies, short, long, UTF-8 and burst data both ways, sends right after an ESP32 reboot, `reset()`, and `chat_hm10-esp32.py`). Setup and the exact command are in [tests/README.md](tests/README.md). It needs both boards on USB, the ESP32 already targeting the HM-10's name, and the Mega running a plain `Serial` (115200) ↔ `Serial3` pass-through, not `init_hm10.ino`. About 2 minutes, 22 checks, exit code 0 means pass. Run it after any change to the firmware or to `hm10_esp32_bridge.py`.

- The ESP32 and the Mega both enumerate as `/dev/ttyUSB*`, in plug order. Identify the ESP32 with `python -m esptool -p /dev/ttyUSBx chip-id` (ESP-IDF's Python), or read each port for 4 s at 115200: the ESP32 prints ESP-IDF logs, the Mega prints the sketch's text.
- `idf.py monitor` needs a TTY. From a script, read the port with pyserial at 115200 (pulse RTS to reset the board).
- Opening the Mega's port resets the Mega. With `init_hm10.ino` loaded, that factory-resets the HM-10 and drops the BLE link.
- To see only data on the ESP32's port: `idf.py monitor --print_filter bt_com:I`.
- The nRF Connect phone app shows whether an HM-10 is advertising and what name it has.

## 8. Known open issues

Fixed items are left out: see the git log, and [HANDOVER.html](HANDOVER.html) section 4 for the bench evidence behind the fixes made at the 2026-11 handover.

**Open:**

1. **Keep testing on different PCs.** This is the most important item. The direct path depends on each PC's operating system, Bluetooth adapter and driver; the ESP32 path on the CH340 driver. Tested so far: ESP32 path on Linux and Windows 11, direct path on Linux. Untested: macOS on either path, the direct path on Windows. Record each result in [HANDOVER.html](HANDOVER.html) section 7.
2. **The AT helpers throw away car data.** `get_hm10_name()`, `get_status()` and the others read and discard any BLE data that arrives while they wait for their reply. `listen()` also drops any car message that starts with `OK+`. From code reading, not seen in use. Until fixed, call the helpers before the chat, not during it (the chat script does).

**Accepted as is** (reviewed at the 2026-11 handover, no work planned):

- **Message format between PC and car:** a newline ends a message. The student guide shows it on both sides (`send("...\n")`, `Serial3.readStringUntil('\n')`). `chat_hm10-esp32.py` does not add it; the chat is interactive, so that is fine.
- **A failed connect stops the scan.** If `esp_ble_gattc_open` fails ("open failed" in the log), `connect` stays true and no new scan starts. From code reading, never seen on hardware. `AT+RESET` recovers.
- **Unused menuconfig options** `CONFIG_HM10_DEVICE_NAME` / `CONFIG_HM10_DEVICE_MAC` are defined but never read. Harmless; the name is set with `AT+NAME`.

**Known limits:**

- **`AT+NAME` reads at most 32 bytes in total**, so a name longer than 25 characters is cut and the rest goes to the HM-10 as data. HM-10 names are at most 12 characters, so this only matters for typos.
- **ESP32 path speed**: at most about 400 bytes/s (10 bytes per 25 ms, write with response). Estimated from the code, not measured.
- **Reopening the ESP32's port** was once seen to cause an extra disconnect and reconnect (`OK+LOST`, `OK+CONN` on the car). Not investigated.
- **No tests run without hardware.** The end-to-end test needs the bench (section 7).

## 9. Git conventions

- `main` is the version students use. It must always run. Develop on a branch started from `main` (`git switch -c <branch> main`) and merge when the hardware test passes (section 7).
- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): description`, for example `fix(esp32-hm10): keep scanning until the hm-10 is found`. Types in use: `feat`, `fix`, `docs`, `chore`, `refactor`.
- One commit per change; no fix-up commits. Amend or `git reset --soft` and recommit instead.
- Update the guide that describes what you changed: `beginner_guide.md` for anything a student does, `TA_GUIDE.md` for setup and behaviour, this file for build and internals.
